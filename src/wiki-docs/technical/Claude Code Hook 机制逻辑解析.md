# Claude Code Hook 机制逻辑解析

> 本文聚焦 Hook 机制的**逻辑与设计意图**：它解决什么问题、每个环节在决策什么、各事件为何存在、各系统如何协作。
> 不罗列具体脚本、函数签名或 schema 字段——那些是实现细节，本文只讲"机制为什么是这样"。
>
> 说明：以下分析均基于源码推导出的行为逻辑，可作为行为基准，不依赖具体实现文件。

---

## 1. Hook 是什么，解决什么问题

Hook 是一套**事件回调机制**：当 Claude Code 的主流程走到某些关键节点时，允许外部代码"插一脚"，同步或异步地观察、修改甚至阻断这个节点。

它要解决的根本问题是：**主循环不可改，但行为必须可扩展。**

CC 的核心是一条固定运行循环（读输入 → 调模型 → 调工具 → 生成回复 → 循环）。这条循环本身不该被改来改去。但不同用户、不同团队、不同企业有千差万别的诉求：审计、安全拦截、上下文注入、权限代答、远程策略……如果都塞进主循环，循环会爆炸。Hook 的解法是：**主循环在关键节点广播"事件"，外部以"订阅-响应"方式参与，主循环不变。**

因此 Hook 的价值主张有四点：

1. **非侵入**：主循环只多一句"广播事件"，其余逻辑全部外挂。
2. **可在执行期改变行为**：hook 不仅能看（旁路观察），还能改（注入、阻断、代答）。
3. **事件即契约**：一套固定的 27 事件，让所有扩展方对齐同一套插桩点。
4. **策略可集中**：企业/托管方可集中下发规则，不必改每个用户的代码。

## 2. 两个关键维度：类型与事件

理解 Hook 机制，抓住两个维度即可——**hook 长什么样（类型）** 与 **在哪些节点起作用（事件）**。

### 2.1 Hook 的类型：六种形态，按"谁来执行"划分

Hook 按"由谁承载这段判断逻辑"分为六类，每类解决特定的"谁来算、怎么算"问题：

1. **命令型（子进程执行）**：把判断交给一段外部命令/脚本。最通用、最简单——任何会写命令的人都能用，是默认形态。可声明为同步或异步：同步则主循环等它；异步则它先应答、后台跑、跑完再回灌，不拖慢主循环。用一个"条件"可表达"仅当某参数匹配才执行"。
2. **提示词型（模型代答）**：把判断交给一次大模型调用。hook 是一段给模型的指令，模型返回"通过/理由"。适合需要"理解语义"的判定（如"这段用户输入是否越界"），用模型的理解力代替手写规则。
3. **代理型（子代理代答）**：把判断交给一个多轮代理。比单次提示更强——它可以查文件、跑工具、反复推敲后再下结论。适合需要"调查取证"的重型判定（如复杂代码的审查门禁）。
4. **HTTP 型（远程服务代答）**：把判断交给一个远程服务。企业可把判定规则集中在远端、统一更新，本地无需改动。出于安全，这类钩子有限制：不可访问内网任意地址（防 SSRF），只能透传明确允许的环境变量。
5. **回调型（进程内注册）**：把判断逻辑内嵌为进程内回调。用于 CC 内部系统自举（如会话内文件访问授权、Git 提交归属标注），以及无需起进程的轻量场景，外部用户通常不直接配置。
6. **函数型（会话级内存回调）**：把判断内嵌为会话作用域内的 JavaScript 回调，跟着会话临时生效、结束即销毁。适合"只在此次会话有用"的一次性校验，不可长期落盘。

> 一条钩子可以是上述其中一种；同一条"逻辑"可换不同形态承载。形态决定**执行成本、能力边界、是否可分发**，是配置时的核心选择。

### 2.2 事件：循环里的插桩点

事件 = "主循环走到了哪里、发生了什么"。全部 27 个事件分为五类生命周期使命：

**A. 保护工具调用（工具命脉）**
这类事件围绕"工具该不该跑、跑了之后怎么办"做文章：
- 工具**执行前**：拦截、审计、改写入参、替代权限决策。
- 工具**成功后**：后处理结果，甚至替换模型看到的工具输出。
- 工具**失败后**：兜底、告警（不影响已失败的结果）。
- 权限**询问时**：替代用户回答"放行/拒绝"，决定是否中断。
- 权限**被拒后**：决定要不要自动重试。

**B. 把人拉进循环（人机边界）**
- 用户**提交提示词时**：先审一遍用户输入、注入上下文。
- 会话**开始/结束时**：初始化（注入首条消息、启动监听）与善后（清理、上报）的两端收口。
- 模型**每轮回复停止时**：一轮循环的"检查点"，注入下一轮上下文，或决定不再继续。
- 工具环境**就绪时**：在工具都能用之后再做一次注入。

**C. 管理子代理与协作（规模化）**
- 子代理**启动/结束**：按子代理类型注入/善后。
- 团队成员**空闲**、任务**创建/完成**：多代理协作中的心跳与任务流转信号。

**D. 感知状态变化（上下文与环境）**
- 上下文**压缩前/后**：压缩是"丢信息"的高危动作，前端通知外部备份/校验。
- **配置变更**、**指令加载完成**、**文件变化**（按文件名匹配）、**目录切换**：对这些环境/状态变化做联动。

**E. 打通外部世界（集成）**
- 系统**通知**：把 CC 内部通知（升级提醒、补丁提示等）桥接到外部。
- MCP 工具发出**澄清请求 / 获得澄清结果**：把"要人回答"的交互改造成"程序应答"。
- **工作树创建/移除**：版本控制资产的生命周期联动。

> 设计要义：事件不是随意堆的，而是精准落在"会有害的、要收口的、要同步的、要编程化的"四个信号点上。事件一旦定了，所有扩展方共用同一套约定，不必各写各的插桩。

### 2.3 27 个 Hook 事件逐个解析

逐一列出每个事件**在哪个节点触发、它存在的意义是什么**：

**A 组 · 工具生命周期**

- **PreToolUse**——工具将要被调用之前。作用：门前的"审核与改判"。可拦截，可审计，可改写入参，并参与"放行 / 拒绝 / 询问"裁决。是最常被用来做安全闸门的事件。
- **PostToolUse**——工具成功返回之后。作用：事后的"整治与留档"。可后处理结果，甚至替换模型实际看到的工具输出。
- **PostToolUseFailure**——工具执行失败之后。作用：失败后的"告警与兜底"（不改变已经失败的结果）。
- **PermissionRequest**——权限弹窗即将弹出、等待用户决定之时。作用：把"要不要放行"外包给程序。放行时可改写入参并可落一条新权限规则；拒绝时可直接中断工具调用。是"无人值守权限"的入口。
- **PermissionDenied**——某次调用已被拒绝之后。作用：决定是否自动重试，形成"拒绝 → 纠正 → 重试"的闭环。

**B 组 · 人机边界与会话**

- **UserPromptSubmit**——用户提交提示词之时。作用：先审一遍用户输入，并可注入额外上下文。是"企业级输入过滤"的主战场。
- **SessionStart**——会话开始之时。作用：注入首条系统消息、启动监听、做初始化。属于低噪声生命周期事件，始终对外广播。
- **SessionEnd**——会话结束之时。作用：清理、上报、收口善后（会话级钩子在此时被整体清除）。
- **Stop**——模型每轮回复停止之时。作用：一轮循环的检查点——注入下一轮上下文，或决定这轮就此结束。是"持续监督、逐轮复查"型 hook 的核心挂点。
- **StopFailure**——停止流程发生异常/被中断之时。作用：兜底清理，避免"停了但没干净地停"。
- **Setup**——工具环境就绪之后。作用：在工具都可用时做最后一次注入/准备。属于低噪声生命周期事件，始终对外广播。

**C 组 · 子代理与多代理协作**

- **SubagentStart**——子代理启动之时。作用：按子代理类型向它注入上下文。"停止"事件在此会被翻译成"子代理停止"来对齐语义。
- **SubagentStop**——子代理结束之时。作用：收口、汇总子代理产出。
- **TeammateIdle**——团队成员空闲之时。作用：多代理协作的"心跳/唤起"信号，主循环据此决定是否派新活。
- **TaskCreated**——任务被创建之时。作用：任务流转的起点通知。
- **TaskCompleted**——任务完成之时。作用：任务流转的终点通知。

**D 组 · 上下文与环境感知**

- **PreCompact**——上下文压缩之前。作用：在"将要丢信息"这个高危动作前通知外部备份/校验。
- **PostCompact**——上下文压缩之后。作用：校验压缩结果、必要时补回关键上下文。
- **InstructionsLoaded**——指令（项目/全局指令）加载完成之后。作用：感知当前生效的指令内容，据以调整行为。
- **ConfigChange**——配置发生变更之时。作用：感知配置变化并联动（也是配置文件热重载的触发信号）。
- **FileChanged**——被监听的文件发生变化之时（按文件名匹配）。作用：形成"看文件变化做事"的响应式能力。
- **CwdChanged**——工作目录切换之时。作用：联动感知目录变更。

**E 组 · 外部集成与通知**

- **Notification**——系统发出通知（如升级提醒、补丁说明）之时。作用：把内部通知桥接到外部系统。
- **Elicitation**——MCP 工具发出澄清请求（需要人补充信息）之时。作用：把"要人回答"改造成"程序自动应答"。
- **ElicitationResult**——获得澄清结果之时。作用：把澄清结果回传给流程。
- **WorktreeCreate**——创建 git 工作树之时。作用：版本控制资产创建的生命周期联动。
- **WorktreeRemove**——移除 git 工作树之时。作用：版本控制资产销毁的生命周期联动。

> 逐个看下来：每个事件都对应一个"外部应当有介入时机"的具体节点——或需保护（有害）、或需收口（善后）、或需同步（状态变化）、或需编程化（本要人来做）。事件集合就是 CC 向外承诺的"可介入点全集"。

### 2.4 响应：hook 能把"发生的事"变成"什么结果"

事件是"发生了什么"，响应决定"接下来怎么办"。hook 的响应本质上有**五档能力**，由弱到强：

1. **只观察**：记录、上报、遥测，不改变主流程。
2. **补充**：注入上下文 / 附加上下文，让模型下一轮看到更多。
3. **改写**：修改工具入参、替换 MCP 工具输出、注入首条用户消息。
4. **裁决**：对权限或继续与否给出放行 / 拒绝 / 询问三态。
5. **阻断**：返回阻塞错误 / 触发中断，直接叫停当前动作。

这五档对应主流程"可以被影响"的五个层级，由浅入深。hook 越用力，对主流程的干预越强，因此机制上也设计了门控（见第 4 节）来约束"哪层干预被允许"。

## 3. 匹配机制：事件来了，谁响应

一句话：**事件广播出去，系统要从所有已配置的 hooks 里筛出"该响应这一条"的那几个。** 匹配不是"所有 hook 都跑"，而是"精确挑人"。逻辑上分四层，层层收窄：

**第一层：按事件分组（最粗的筛）**
hooks 天生按事件归类——每个事件名下挂着若干 hooks。事件发生时，只可能从"该事件名下"的 hooks 里挑，别的事件的 hook 一律不参与。这是最基础的分桶。

**第二层：按匹配对象（按"这条是什么"筛）**
事件在触发时携带一个"当前对象"，系统用约定的字段逐项比对：
- 工具事件：看**本次调用的是哪个工具**（按工具名比）。
- 子代理事件：看**启动的是哪种子代理**。
- 通知事件：看**通知类型**。
- 文件事件：看**变化的文件路径**。
- MCP 澄清事件：看**来自哪个 MCP 服务**。
- 部分事件没有匹配对象，则"凡是响应这个事件的 hook 都算候选"。

匹配对象使同一个事件能按"具体对象"差异化响应——同样是工具事件，对 Bash 和对 WebFetch 可以走完全不同的 hook。

**第三层：按条件（按"参数值"再筛一层）**
在对象匹配之上，还可再挂一个"条件"（语义借用权限规则，例如"仅当 Bash 的参数匹配 `git *` 时才响应"）。条件基于**本次的实际参数**判断，命中才把 hook 列为候选。这一层的核心价值是**预先过滤**——条件在真正执行（起进程 / 调模型）之前就判断，把不相关的 hook 挡在门外，省掉无谓的开销。

**第四层：去重与来源标记（收尾定案）**
候选确定后：
- **去重**：内容相同的 hook（同样命令、同样条件）只保留一份，避免同一逻辑被重复执行。
- **标记来源**：登记每个候选来自哪个来源（配置文件 / 会话 / 插件 / 技能）。来源标记在后续的"策略过滤"与"上下文注入"中，决定它被信任到什么程度。

> 匹配的本质：**层层收窄**——先按事件分桶，再按对象，再按条件，最后去重定案。越往内层越精确，目标是"只让真正该响应的 hook 跑，并且在跑之前就把无谓的执行挡掉"。它是"主循环不可变、行为可扩展"这一总目标在"选人"环节的落实：扩展方只需在正确的事件下、挂上带正确对象与条件的 hook，系统就会自动把它接到对应的调用上。

## 4. 谁来指挥：执行链路与门控

一条 hook 从触发到生效，逻辑上经历四个阶段，每一阶段都是一个"决策点"：

**阶段一：该不该跑？（门控）**
不是任何 hook 在任何时候都能跑。执行前有几道闸门按序拦截：
- 若策略/托管方明确"禁用所有 hooks"——直接不跑（含托管 hooks）。
- 若处于"简化模式"——不跑。
- 若针对的是未受信任项目的敏感操作——出于安全跳过（不轻易起进程）。

**阶段二：哪些 hook 会响应这个事件？（匹配）**
一个事件广播出去，系统要在配置好的 hooks 里挑出"该响应这一条"的那些。靠"按事件分桶 → 按对象匹配 → 按条件过滤 → 去重并标记来源"层层收窄，详见第 3 节。

**阶段三：响应如何执行？（执行）**
- 同一事件的多个候选 hook **并行**执行，互不等待，各自独立超时。
- 执行可能同步等待结果，也可能**异步**——hook 自己决定"我一时算不出来，先在后台跑，跑完回灌"。异步让"慢评估"不拖慢主循环，是支撑"每轮复查"这类用例的关键设计。
- 每条 hook 都有独立的超时上限，避免一个卡死的 hook 拖垮整轮。

**阶段四：结果如何裁决？（聚合）**
- 多个 hook 的裁决要合并成一个最终结论。合并的关键是"**最保守者胜出**"：任何一条否决就否决；没有否决时，任何一条要问人就问人；全放行才放行。
- 其它结果（注入的上下文、首条消息、监听路径、改写后的输入、替换的输出）逐条收集，喂给触发点。
- 阻塞错误、中断信号会被立即上抛，直接叫停当前动作。

> 逻辑主线一句话：**先门控问"能不能跑"，再匹配问"谁来跑"，再执行问"跑出什么"，最后聚合问"听谁的"**。越往后，越体现"外部想干预多深，都在这套管线里被显式编排"。

## 5. 权限：Hook 与主流程最深的一层交互

Hook 对主流程影响最深、也最微妙的是**权限**。这里的关键不是"hook 说了算"，而是"hook 的意见要和既有规则、和用户弹窗精确地融合"，且有一整套"谁压谁"的优先级。

### 4.1 执行前：工具执行前的裁决并入既有权限体系

当工具要被调用前，hook 可以先给出允许 / 拒绝 / 询问。

- **允许**：hook 说"可以"，但**不等于**直接放行。系统仍会复查既有权限规则与必要的手续：
  - 如果既有规则明确**拒绝**——规则压过 hook，照拒。
  - 如果既有规则要求**询问**——仍要弹窗，hook 的"允许"不能跳过用户确认。
  - 如果工具本就要用户参与（交互式），且 hook 自己能补上交互所需的输入——则视为交互已满足，免去弹窗。
- **拒绝**：hook 说"不行"，立即拒，通常不再给其它机会。
- **询问**：把 hook 的"问一下"传递成一次带条件的能力请求，由用户最终拍板。

> 设计要义：hook 不是权限系统的"后门"，而是**一个平级的裁决输入**。它的意见会被纳入统一合并，且**既有安全规则永远享有最终否决权**。这保证了"外部可参与，但不可绕开安全底线"。

### 4.2 询问时：把"是否放行"外包

还有一种更正式的渠道：当权限弹窗**即将弹出**、等待用户决定时，可以让 hook 先应答：
- hook 若**允许**：可顺带改写入参、并可持久化新的权限规则（下次不再问）。
- hook 若**拒绝**：直接拒绝，且可要求**中断**整个工具调用。

这打开了完全"无人值守"的权限路径：企业把判定逻辑放远端，用户面几乎不再弹窗。

### 4.3 被拒后：失败闭环

某次调用已被拒绝后，hook 还能决定"要不要自动重试"。这给了从"拒绝"到"纠正后重试"的闭环能力。

> 权限逻辑的总纲：**让外部能参与"该不该放行"的判定，但安全底线（既有规则）恒定不可绕过；能落地的判定（允许）还要补全必要手续，不能被 hook 一句话省掉。**

## 6. 与其它系统的协作

Hook 不是孤立存在的，它和 CC 的几个扩展体系互为表里。

### 5.1 与权限系统的关系

（见第 5 节）一句话：hook 是权限判定的**一个参与者**，参与合并，但不拥有最终决定权。

### 5.2 与 Skill / Agent 的关系

Skill 和 Agent 可以在自身定义里**附带声明 hooks**，这些 hooks 在 Skill/Agent 被启用时，作为**会话级**钩子临时生效：

- 作用域跟着 Skill / Agent 走，**会话结束即自动清除**，不落盘、不留后患。
- 标记为"一次性"（once）的 hook，首次成功执行后**自动移除**——适合"只跑一次"的初始化。
- 一个很关键的语义对齐：Agent 这种子代理完成时，真正触发的是"子代理停止"而非普通的"停止"。因此在给 Agent 注册 hooks 时，系统会自动把"停止"事件**翻译成"子代理停止"事件**，让语义与真实触发点对齐。
- Skill 的目录会成为其 hooks 可见的"根目录"，供 hook 引用自身资源。

### 5.3 与插件系统的关系

插件可以**随插件分发** hooks（而不是让每个用户手动配）。系统会把插件的 hooks 装上插件身份的标记：

- 带上插件上下文的 hook，在执行时能拿到该插件的目录、选项等**专属环境**。
- 插件启用/禁用变化时，hooks 会被**热重载**——且替换是"整批原子交换"，避免中途出现"旧 hook 已死、新 hook 未生"的缝隙。
- 对外发起请求的 hook（如 HTTP 类）有**安全约束**：不能打内网任意地址（防 SSRF），只能透传明确允许的环境变量。

### 5.4 与 SDK / 外部消费方的关系

对 SDK、远程会话等外部消费方，Hook 机制提供**事件流订阅**：

- 有两类事件**始终**对外广播（生命周期类，噪声低）；其余事件默认不广播，只有显式开启"全部事件"才广播——用"默认克制、按需放开"控制流量。
- 没有接收者时，事件会**暂存排队**（有上限），一旦有接收者即可回放，避免"广播得太早没接到"。
- 异步 hook 有专门的后台注册与唤醒管理，支撑"慢 hook + 后续回灌"。

### 5.5 与消息 / UI 系统的关系

hook 的各类结果会**转译成会话里的消息附件**：成功、阻塞错误、非阻塞错误各有呈现。多条 hook 的进度会被**折叠成摘要**，避免刷屏。`/hooks` 界面则提供可视化的管理入口，改动即时生效。

### 5.6 与文件监听 / 记忆 / 启动通知的关系

- 启动类 hook 可以请求**监听某些路径**；之后这些路径一变，就触发"文件变化"事件，形成"看文件变化做事"的响应式能力。
- 系统内部大量复用 hook 机制（例如会话内文件访问授权、Git 提交的归属标注），它们以"进程内回调"形式存在，是 hook 机制的一个**内部实现样例**。
- 系统级通知（升级提醒等）也作为事件源开放，可被桥接到外部。

## 7. 来源与配置：多源头、可托管、有层次

Hook 从哪里来、由谁说了算，逻辑上分三层：

**来源层（谁提供 hook）**
- 用户/项目/本地配置文件、策略（托管）配置、插件、会话运行时、内置。来源决定"权限与控制力"。

**配置层（长什么样）**
- 按事件分组的配置，每个事件下可挂多个 hook，每个 hook 可带匹配对象与条件。合并时按"作用域叠加"处理。

**策略层（谁能禁用谁）**
- 最关键的是**级别**观念：托管（策略）设置的优先级高于普通设置。用户或项目设置**无法禁用**托管下发的 hooks；只有托管方自己能"全禁"或"仅托管可改"。还有"仅限插件定制"等更细的策略，可封锁用户在配置层定义的 hooks，而插件渠道不受影响（走不同通道）。

> 配置逻辑的总纲：**多数来源自由叠加，但安全策略永远高一级；跨来源去重时后合并且具更高优先级的来源胜出。**

---

## 8. 与其它扩展机制的区别（定位）

- **与权限规则**：规则是"写死的策略"，hook 是"可编程的判定"。hook 会在规则之外多给一层灵活输入，但规则仍压过 hook。
- **与插件 / MCP**：插件与 MCP 提供"工具/能力"，hook 提供"对主流程的插桩"。能力扩展 vs 行为扩展，互为补充而非替代。

---

## 9. 总结：这套机制设计的核心逻辑

1. **主循环不可变，行为靠外挂**：固定事件点 + 外部响应，是整套机制的地基。
2. **事件即契约**：27 个事件精准落在"有害、收口、同步、编程化"四类信号点上，统一所有扩展方的插桩约定。
3. **干预有层级**：观察 → 补充 → 改写 → 裁决 → 阻断，五档能力由弱到强，机制逐级编排。
4. **有门控、有优先级**："不能跑就不跑""最保守者胜出""安全规则终审"，保证可扩展但不失控。
5. **异步是放大器**：让慢评估不拖主循环，是"持续监督型" hook 得以存在的前提。
6. **与各系统互为表里**：Skill/Agent 带钩子临时生效、插件随包分发、SDK 订阅事件流、权限深度融合——hook 是贯穿这些体系的一根"行为总线"。
