## 1. 核心概念

理解 Skill 机制，最关键的洞察是：**Skill 不是一种独立的系统实体，而是一种「特殊的命令」**。系统内部只有一套统一的命令模型（`Command`），Skill 就是其中 `type` 为 `prompt` 的那一类——它把一段领域指令和可选的参考文件作为「提示内容」交给模型。

因此，Skill 的所有行为（发现、匹配、注入、执行、权限、hooks）都复用了命令系统的既有能力，Skill 的独特之处只在于：它携带**可注入的内容**（`getPromptForCommand`），以及若干 Skill 专属的元数据字段（`allowedTools`、`context`、`agent`、`paths`、`hooks` 等）。

一条 Skill 从诞生到生效，经历了六步：

```
定义 → 注册 → 发现 → 匹配 → 注入 → 执行
```

其中「定义与注册」回答了 Skill 从哪来、以什么形式存在；「发现与匹配」回答了它如何被定位与门控；「注入与执行」回答了它如何影响模型的行为。

## 2. Skill 是什么

### 2.1 Skill = 提示型命令

Skill 的本质是一段「按需加载的领域指令」：平时它不占上下文，只有被调用时才把内容展开注入。这使它区别于始终在上下文里的系统提示，以及一次性执行脚本的本地命令。

### 2.2 Skill 携带的元数据

Skill 区别于普通命令的核心字段分为几组，每一组对应一个能力维度：

- **身份维度**：名称、别名、描述、`whenToUse`（何时使用）——用于被模型或用户找到。
- **调用门控维度**：`disableModelInvocation`（禁止模型调用）、`userInvocable`（允许用户斜杠调用）、`isEnabled`（条件启用）、`isHidden`（从补全/帮助隐藏）。这四个字段共同决定"谁能通过哪条路径调用它"。
- **行为维度**：`context`（内联 or 子代理）、`agent`（fork 子代理类型）、`effort`（推理强度）、`allowedTools`（调用后自动授权的工具）。
- **内容维度**：`getPromptForCommand`（产生注入内容）、`paths`（条件激活）、`files`（内置技能的参考文件）。
- **协作维度**：`hooks`（技能级钩子）、`skillRoot`（技能根目录）、`pluginInfo`（插件归属）。

### 2.3 一个微妙的设计：`source` 的两层含义

系统用两个字段分别记录技能的「来源」与「加载处」：`loadedFrom` 描述它从哪个渠道加载，`source` 描述它在命令生态中的归属。这两个字段容易混淆，而它们对「技能是否出现在模型的 Skill 工具列表」「是否参与内置技能预算豁免」有决定性影响。

这里有一个值得注意的坑：`source` 取值为 `'builtin'` 时，含义是**硬编码斜杠命令**（如 /help、/clear），而不是内置技能。因此，从插件贡献的内置技能必须标注为 `'bundled'` 而非 `'builtin'`，否则它会被排除在 Skill 工具列表之外。这是代码注释里明确提醒的一个易错点。

## 3. Skill 的来源

Skill 按 `loadedFrom` 主分类，对应六种来源渠道：

1. **内置（bundled）**：随二进制打包，在启动时程序化注册，不依赖磁盘文件。
2. **插件（plugin）**：由插件通过技能定义数组贡献，或散落在插件目录的 skills 文件夹。
3. **用户/项目 skills 目录（skills）**：磁盘上按约定放置的 `SKILL.md` 文件，是最常见的用户自定义方式。
4. **废弃 commands 目录（commands_DEPRECATED）**：兼容旧版 `/commands` 格式的后向兼容渠道。
5. **受管（managed）**：由企业/受管策略注入，优先级最高，用于统一管控。
6. **MCP（mcp）**：由 MCP server 提供的 prompt，受特性开关门控。

这六种来源在加载时被聚合到一个统一的命令列表中，彼此通过「先到先得 + 按优先级去重」协调同名冲突（详见第 4 节）。

## 4. 从文件到命令的转换

这是 Skill 的「定义与注册」环节，回答两个问题：磁盘上的技能如何变成系统认识的命令？内置技能又如何注册？

### 4.1 磁盘技能的解析

磁盘上的 Skill 以 Markdown 文件承载，头部 YAML frontmatter 写配置，正文写注入内容。解析过程把 frontmatter 的各字段翻译成命令的元数据，并把正文包进「内容生成器」（`getPromptForCommand`）。

关键点在于**宽容的校验**：frontmatter 中的 `hooks` 等敏感字段用 Schema 校验，但校验失败只是告警而非报错——技能仍然可以加载，只是失去该能力。这体现了"不让一个坏字段毁掉整个技能"的设计取舍。

### 4.2 内置技能的程序化注册

与磁盘技能靠文件解析不同，内置技能在源码里用定义对象直接注册，`getPromptForCommand` 由代码实现（而非从文件读取）。注册时做一次「定义 → 命令」的字段映射，把 `userInvocable` 等定义字段翻译成命令字段，其中 `isHidden` 由 `userInvocable` 派生。

内置技能并非全部无条件注册：部分由特性开关（feature flag）门控，仅在对应功能开启时注册。值得注意的是，其中有三个文件是**空实现占位**——只有开关分支、没有注册任何真实技能，属于为未来功能预留的脚手架，不应视作已激活的能力。

### 4.3 插件与 MCP 的技能接线

- **插件**通过「技能定义数组」声明自己贡献哪些技能，再由一个转换函数把每个定义变成命令。这一层存在的原因，是让插件能以与内置技能相同的形式提供技能，复用同一套定义与注册逻辑。
- **MCP** 在当前源码快照中只是一个占位实现（返回空列表），但保留了「构建器注册表」的依赖注入机制，用于规避循环依赖——即允许 MCP 客户端复用统一的技能解析与命令构造能力，而不在模块间形成环。

### 4.4 去重与优先级

当多个来源出现同名技能时，系统需要裁决谁生效。它以「文件身份」为准（解析符号链接后的真实路径）判定是否是同一个技能，并按来源优先级**先到先得**：

```
受管 > 用户目录 > 项目目录 > 附加目录 > 废弃目录
```

高优先级来源先注册，后到的同名技能被丢弃。这一机制保证了受管策略能覆盖用户自定义、用户能覆盖项目默认。

## 5. 发现与加载

### 5.1 扫描与加载

系统在运行时**惰性扫描**技能目录：识别技能文件、解析 frontmatter、构造命令。它同时维护两条加载链路——一条主链路针对现代的 `SKILL.md` 目录格式，另一条针对废弃的 `/commands` 目录格式以保后向兼容。

### 5.2 热重载

技能目录被文件监视器持续监听，文件变更会触发缓存清除与重新加载，使技能修改无需重启即可生效。这是"配置即代码、改完即用"体验的基础。

### 5.3 条件技能与动态技能

这是 Skill 机制中两个体现"按需"哲学的进阶形态：

- **条件技能**：在 frontmatter 声明 `paths`，只有模型实际触碰（读写）匹配的文件后才「激活」可见。这使技能可以高度聚焦、平时几乎不占模型注意力。
- **动态技能**：当模型触碰文件时，系统沿着该文件的路径向上寻找技能目录，动态发现并加载新技能。这使技能可以"就近"存放（如放在某个子项目内），无需集中登记。

两者共同的本质是：**技能的存在是声明式的，技能的生效却是按需的**——不相关的技能不会打扰模型。

### 5.4 命令聚合

所有来源的技能（内置、内置插件、目录、workflow、插件、MCP）最终在一条合成路径中被合并成一个统一列表，并在此处完成可用性过滤与动态技能插入。这是一个典型的「多源汇聚、单点消费」结构：下游（匹配、注入、展示）只面对一份统一的命令集合。

## 6. 匹配与门控

### 6.1 名称解析

所有对技能的引用（用户斜杠、模型 Skill 工具）都会收敛到同一个按名称/别名查命令的入口，保证两边看到的技能集合与匹配规则一致。用户侧另有独立的模糊补全逻辑，负责在输入前缀时给出候选。

### 6.2 双调用入口与各自的门

Skill 有两条调用路径，各自守着一道不同的门：

- **用户斜杠调用**（输入 `/技能名`）：过 `userInvocable` 这道门——不允许用户调用的技能（`userInvocable: false`）在此被拒。
- **模型调用**（Skill 工具）：过 `disableModelInvocation` 这道门——标记为禁止模型调用的技能，模型一调用就报错。

两道门相互独立：一个技能可以「只允许用户显式调用」而「对模型隐藏」，也可以反过来「只允许模型自动触发」而「从用户补全隐藏」。这种双向门控让技能作者能精确控制谁在什么场景调用它。

两条路径最终汇合到同一个执行入口，因此技能内容的注入、hooks 的注册、调用记录的登记都只发生一次，不会因双路径而重复。

### 6.3 模型可见性的三层过滤

模型眼里能看到哪些技能，由三个不同的列表分别管辖，各有偏向：

- **Skill 工具可调用列表**：决定模型能实际调用哪些技能，排除 `disableModelInvocation` 的。
- **斜杠工具技能列表**：用于技能发现与计数，而非调用授权，标准更宽（甚至把 `disableModelInvocation` 当作技能标识）。
- **MCP 技能列表**：单独的受开关门控的渠道。

一个有价值的细节：插件/MCP 来源的技能需要**显式的描述**才会出现在模型的 Skill 工具列表中——系统宁缺毋滥，避免无描述的半成品技能进入模型视野。

## 7. 注入与执行

### 7.1 内容注入管线

当技能被命中，系统把它的内容注入模型上下文，走一条统一的管线：

```
补充技能基目录说明
  → 替换参数占位（用户传入的参数）
  → 替换会话级变量
  → 执行提示词内嵌的 shell 命令（生成动态内容）
  → 输出为可注入的内容块
```

其中，「基目录说明」告知模型技能参考文件在哪里、可按需读取；「执行提示词内嵌的 shell 命令」让技能能动态生成注入内容（如查询系统状态后再指导模型）。出于安全考虑，MCP 来源的技能**跳过** shell 命令执行——外部来源的内容不能被赋予执行能力。

### 7.2 内联与会话隔离（fork）

技能的执行方式由 `context` 决定：

- **内联（inline）**：内容直接注入当前对话，模型在同一上下文中继续，适合多数技能。
- **子代理（fork）**：在一个独立的子代理上下文中执行（拥有独立的 token 预算），再回传结果，适合大型任务，避免污染主对话。

fork 方式下，技能可通过 `agent` 字段指定子代理类型，未指定则回退通用类型；同时它把 `allowedTools` 转成受限的工具集，并把 `model` 作为子代理的模型覆盖。这让技能能声明"我是一个需要专用代理/专用模型的任务"。

### 7.3 模型端的 Skill 工具

模型通过一个名为 `Skill` 的工具调用技能，入参只有两个：技能名和可选参数。调用前经历完整的校验与授权：

- **校验**：确认技能存在、可被模型调用、是提示型命令。
- **授权**：遵循命令权限系统，但有一个"安全属性自动放行"机制——若技能的全部字段都在一个安全白名单内，则无需用户逐次授权，直接放行；否则默认询问用户。

调用成功后，技能注入内容，并把声明的 `allowedTools` 立即并入本次调用的放行规则，`model`/`effort` 覆盖本次会话的模型与推理强度。整个过程对模型而言是"一次技能调用，附带一组本次生效的授权与模型调整"。

### 7.4 技能发现列表的注入

模型是如何知道有哪些技能的？不是一开始全部塞进上下文，而是通过一个动态注入的「技能清单」attachment，在轮次变化时按需补充：

- **预算约束**：清单总预算约为上下文窗口的 1%，每项描述上限 250 字符——防止清单本身挤占上下文。
- **增量去重**：每个代理只收到此前未见过的"新"技能，避免重复注入浪费 token。
- **内置豁免**：内置技能不参与预算截断（始终完整给出），用户/插件技能则按预算截断。

这意味着：**并非所有技能描述都会进入模型上下文**。模型看到的是被预算裁剪过的发现用清单，完整的技能内容在真正调用时才加载。压缩（compaction）后清单会重新暴露，保证模型在大上下文会话中仍能发现技能。

### 7.5 内置技能参考文件的解压

部分内置技能携带**参考文件**——一份随技能捆绑、首次调用时解压到磁盘的内容，供模型按需 `Read`/`Grep`。这样做既避免把冗长文档常驻上下文，又让模型能按需检索细节。

这个解压过程是严格的安全边界：解压目录带每次进程随机的随机串（防预建符号链接攻击）、显式设置私有文件权限、禁止覆盖既有文件、拒绝路径穿越。这体现了"可执行上下文的内容注入"与"文件系统写入"之间的信任边界设计——技能内容作为模型输入是可信任的，但对磁盘的写入必须逐项设防。

## 8. Skill 的组织生态

Skill 不是孤立运行的，它与系统的多个子系统协作，构成一张网：

### 8.1 与 Hooks

技能可在自身携带 `hooks`，在**技能被调用时**注册为「会话级」钩子（而非全局配置），并按会话隔离。关键设计：

- **懒注册**：技能不调用就不注册，调用时才生效，符合"按需"哲学。
- **按会话隔离**：一个会话里注册的技能 hooks 不影响其他会话。
- **单次钩子**：声明 `once` 的钩子在首次成功后自动移除。
- **权限门控**：钩子注册本身受系统策略门控——在仅限可信插件的场景下，非受信来源的技能不能被授予钩子能力。

技能 hooks 是叠加在设置中的全局/项目钩子之上的**附加层**，它们由统一的钩子执行层汇集执行。

### 8.2 与 Plugins

插件通过技能定义数组贡献技能，与内置技能共用同一套定义与转换逻辑。插件技能带插件归属标记，用于在遥测中区分官方与第三方。

### 8.3 与 Agents

- 技能的 `agent` 字段可指定 fork 子代理类型。
- 调用记录（`addInvokedSkill`）**按子代理作用域**登记，上下文压缩时只恢复当前子代理的技能，防止跨子代理内容泄漏。

### 8.4 与工具系统

- 技能的 `allowedTools` 在调用后立即并入本次授权规则。
- 存在一个安全属性白名单：字段全部安全的技能可免逐次授权。

### 8.5 与 MCP

MCP 技能是独立的受开关门控的渠道；且出于安全，其内容注入**跳过** shell 命令执行。当前源码中 MCP 技能为占位实现。

## 9. 设计意图

纵观整套机制，可以提炼出几个贯穿始终的设计哲学：

1. **统一模型、按需加载**：Skill 不是新实体，而是命令的一种——所有能力复用命令系统；且技能的内容平时不占上下文，只有调用才注入。
2. **声明式定义、按需生效**：技能可以是条件触发的（触碰文件才激活）、动态发现的（就近发现）、预算裁剪的（清单按 1% 预算截断）。系统反复权衡"让模型知道哪些技能"与"控制上下文占用"。
3. **双向门控、精确归因**：用户路径与模型路径各守一道门（`userInvocable` / `disableModelInvocation`），配合 `isEnabled` 条件值和 `isHidden` 派生隐藏，让技能作者能精确控制可见性、可调用性与激活条件。
4. **多源汇聚、去重裁决**：六种来源在统一列表中按优先级先到先得，受管优先于用户、用户优先于默认。
5. **内容可信、写入设防**：技能内容作为模型输入可信，但对文件系统的写入（参考文件解压）做了逐层安全设防（随机目录名、私有权限、防覆盖、防穿越）。
6. **协作而不耦合**：与 hooks（懒注册、会话隔离）、plugins（统一定义）、agents（作用域隔离）、tools（白名单放行）、MCP（独立渠道）的协作都遵循"附加层"模式，互不侵入核心。
